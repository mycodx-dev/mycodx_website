# 관리자 검색·소식 작성 기능 적용

이번 변경은 채용 검색과 소식 CMS 코드 및 SQL 파일을 준비한 것입니다. 실제 Supabase SQL 실행, Vercel 환경변수 변경, 커밋·푸시·배포는 아직 하지 않았습니다. 기존 문의·채용 접수/SMTP/Resend, 비공개 이력서 버킷, `vercel.json`, 운영 `mycodx.com` DNS와 원본 저장소는 유지합니다. 새 의존성이나 유료 기능을 추가하지 않습니다.

## 직접 적용할 순서

**새 코드를 배포하기 전에 SQL을 적용합니다.** 이전 코드가 사용하는 RPC는 유지하므로 먼저 SQL을 적용해도 기존 관리자 기능은 계속 사용할 수 있습니다. 기존 `202610300001_recruit.sql`은 재실행하지 않습니다.

1. Supabase SQL Editor → New query, Role `postgres`에서 다음 파일을 **번호순으로 하나씩** 전체 실행합니다.

   | 순서 | 파일 | 변경 내용 |
   | --- | --- | --- |
   | 1 | `supabase/migrations/202611040001_admin_search.sql` | 전체 지원서 검색·필터 RPC 추가. 지원자 데이터 수정 없음 |
   | 2 | `supabase/migrations/202611040002_news_cms.sql` | 소식·변경 이력 테이블, RLS, 서버 전용 RPC 생성 |
   | 3 | `supabase/migrations/202611040003_news_seed.sql` | 기존 `news.json`의 소식 2건을 동일 주소·사진·본문으로 가져오기 |

   각 파일은 트랜잭션으로 실행됩니다. 이미 적용한 파일은 `Already applied` 오류로 중단합니다. 오류가 나면 다음 파일로 넘어가지 말고 원인을 확인합니다. 재실행을 위해 테이블이나 기존 지원서를 지우지 않습니다. 가져오기 SQL은 기존 DB 글을 덮어쓰지 않으며 동일 slug가 이미 있으면 전체 작업을 중단합니다.

2. `supabase/verification/04_admin_news_verify.sql`을 별도 쿼리에서 실행합니다. 이 파일은 읽기 전용입니다. 예상 결과:
   - 마이그레이션 버전 3개
   - `news_posts`, `news_audit_logs` RLS=true
   - anon/authenticated/service_role의 테이블·컬럼 직접 접근=false
   - 새 RPC 6개: postgres 소유, SECURITY DEFINER, 빈 search_path, anon/authenticated 실행=false, service_role 실행=true
   - 최초 소식 total=2, published=2, private_drafts=0
3. Vercel → 프로젝트 → Settings → Environment Variables에 **`NEWS_CMS_ENABLED=true`**, Type **Config**를 등록합니다. 실제 사용하는 `vercel.app` 배포가 Production이면 Production에 등록합니다. Preview에서도 시험한다면 해당 환경에도 등록합니다. Supabase URL/키와 관리자 계정은 기존 것을 사용합니다.
4. 변경 코드를 커밋·푸시하고 Vercel 배포 Ready를 확인합니다. 기존 배포는 환경변수 변경만으로 갱신되지 않습니다.
5. `https://mycodx-website.vercel.app/admin`에서 로그인하고 채용 관리·소식 관리 메뉴를 확인합니다. 운영 도메인 연결은 필요하지 않습니다.

커밋 메시지: `feat: 관리자 지원자 검색·필터 및 Supabase 소식 작성 기능 추가`

## 채용 검색·필터

- 검색 입력 후 검색 버튼/Enter: 이름·이메일·연락처의 부분 일치. 영문 대소문자 구분 없음. 전화번호는 하이픈 없는 숫자로도 검색합니다.
- 지원 분야·경력 구분·확인 상태를 조합할 수 있습니다. 선택 시 첫 페이지로 돌아갑니다. 초기화는 모든 조건을 해제합니다.
- DB에서 조건을 적용한 뒤 30명씩 읽습니다. 현재 페이지에 없는 지원자도 검색됩니다. 접수 완료되고 보관 기한이 남은 자료만 조회합니다.
- 분야·경력 선택지는 전체 유효 지원서에 실제 저장된 값으로 구성됩니다. 언어별로 다른 문구가 저장됐다면 별도 항목으로 표시됩니다. 임의로 기존 지원자의 값을 바꾸지 않습니다.
- 검색어는 POST 본문으로만 보내며 URL·localStorage·일반 서버 로그에 저장하지 않습니다. SQL 매개변수와 문자 그대로의 부분 검색을 사용하므로 `%`, `_`, 따옴표는 검색 구문으로 실행되지 않습니다.

## 소식 작성·게시

자동 번호 변경을 적용할 때는 [소식 자동 번호 적용](news-numbering-setup.md)의 추가 SQL을 먼저 실행합니다. 아래 글 주소 입력·고정 안내는 자동 번호 적용 전 방식입니다. 적용 후에는 주소 입력 없이 첫 임시저장 시 번호가 발급됩니다.

1. 관리자 → **소식 관리 → 새 소식 작성**을 누릅니다.
2. 글 주소(영문 소문자·숫자·하이픈), 게시 날짜, 분류, 제목, 요약, 본문을 입력합니다. 한국어 제목은 필수이고 영어는 선택입니다. 기존 일본어·프랑스어 필드는 저장 시 보존되며 이번 편집 화면은 한국어·영어를 제공합니다.
3. 필요하면 대표 이미지, 추가 사진(최대 10장), 관련 링크를 입력합니다. 이미지는 기존 `/uploads/...` 경로나 HTTPS 주소를 사용합니다. **파일 직접 업로드는 이번 단계에 포함되지 않습니다.** 이력서 저장 버킷은 소식 사진에 사용하지 않습니다.
4. **임시저장**하면 DB에 저장되지만 공개되지 않습니다. 본문 미리보기는 일반 텍스트 표시만 지원합니다. HTML/스크립트를 실행하지 않습니다.
5. **게시**를 누르고 확인하면 저장된 초안이 공개본으로 복사됩니다. 저장하지 않은 변경사항이 있으면 게시할 수 없습니다.
6. 이미 게시한 글을 수정하고 임시저장해도 홈페이지에는 이전 공개본이 유지됩니다. 다시 게시할 때 수정 내용이 반영됩니다.
7. **비공개 전환**은 공개본을 제거하고 초안을 보존합니다. 새로 조회한 목록·상세에서 보이지 않습니다. 이미 열어 둔 탭이나 외부에 저장한 사본까지 회수하지는 않습니다.

글 주소는 최초 저장 후 변경할 수 없습니다. 기존 2건의 `/news/<id>` 주소와 사진 경로는 유지됩니다. 게시 날짜는 표시·정렬용이며 미래 날짜를 선택해도 게시 버튼을 누르면 즉시 공개됩니다. 예약 게시 기능은 없습니다. 목록은 최신순, 관리자·공개 목록 모두 페이지당 20건이며 공개 화면은 ‘소식 더 보기’로 이어 읽습니다.

저장·게시·비공개 전환은 버전 번호를 확인합니다. 다른 관리자의 변경이나 응답 유실로 충돌하면 작성 중인 입력을 유지하고 오류를 표시합니다. `최신 저장본 불러오기`는 현재 입력을 버릴 수 있으므로 필요한 내용을 별도로 보관하고 확인합니다. 새로운 글도 고정 내부 UUID로 저장하므로 같은 요청 재시도가 중복 글을 만들지 않습니다.

## 권한·공개 데이터와 전환

- 기존 `recruit_admins.active=true` 승인 계정이 두 메뉴를 모두 관리합니다. 소식 전담 계정과 채용 담당자를 분리하는 권한 체계는 아직 없습니다. 채용 접근을 허용하면 안 되는 편집자에게 이 허용 목록을 부여하지 않습니다.
- 매 관리자 요청의 Auth 사용자 검증·Origin 검사·승인 목록 확인을 유지합니다. 뉴스 RPC도 승인 여부를 재확인합니다. 모든 직접 테이블 접근은 차단하며 변경은 서버 전용 RPC로 수행합니다.
- `news_posts.draft`와 `published`는 분리됩니다. 공개 `/api/news`는 게시된 스냅샷만 반환하고 초안·관리자 UUID·변경 이력을 공개하지 않습니다. 목록 응답에는 긴 본문과 추가 사진을 포함하지 않고 상세에서 별도로 읽습니다.
- `news_audit_logs`에는 저장/게시/비공개 작업과 관리자 UUID·버전·시각을 남깁니다. 본문이나 키는 로그에 넣지 않습니다.
- `NEWS_CMS_ENABLED`를 생략하거나 false로 두면 공개 소식은 기존 JSON 자료를 사용하고 소식 관리자 쓰기는 비활성화됩니다. **true로 전환한 후 API 오류가 나면 옛 JSON으로 자동 복귀하지 않습니다.** 비공개로 바꾼 과거 글이 다시 노출되는 것을 막기 위해 오류·재시도 화면을 표시합니다.
- 명시적으로 false로 되돌리면 저장소의 옛 소식이 다시 공개될 수 있습니다. 기존 글의 비공개 처리 여부를 검토하지 않고 롤백하지 않습니다.
- CMS 전환 이후 소식 원본은 DB입니다. Pages CMS나 `src/content/news.json`을 편집해도 활성화된 홈페이지에는 반영되지 않습니다. 기존 `CMS_GUIDE.md`는 과거 파일 기반 방식 안내이며 현재 저장소에는 `.pages.yml`이 없습니다.

## 검증·백업

로컬 자동 테스트: `npm test`, `npm run lint`, `npm run build`.

`tests/admin-cms.integration.sql`은 **격리된 새 로컬 PostgreSQL 테스트 DB 전용**입니다. 가짜 Supabase 스키마와 역할을 생성하므로 Supabase SQL Editor에서 절대 실행하지 않습니다. 이 테스트는 전체 마이그레이션, 실제 SQL 검색/페이지 이동, 비승인 접근, 초안·공개본 분리, 게시/비공개, 동시 버전 충돌을 검증합니다.

배포 후 가상 지원자 검색, 기존 소식 2건 표시, 새 가상 소식 임시저장 시 미노출, 게시 후 노출, 수정 초안 미노출, 비공개 후 미노출, 비승인 계정 차단을 확인합니다. 실제 프로젝트 설정과 Auth 동작은 배포 후 별도 확인이 필요합니다.

새 `news_posts`와 `news_audit_logs`도 기존 DB 백업 대상에 포함해야 합니다. 이번 변경은 자동 백업·복구 스케줄러를 구현하거나 실행하지 않습니다. 외부 이미지 주소는 DB에 URL만 저장하므로 원본 사진의 백업은 별도로 관리합니다.

권한 근거: [PostgreSQL SECURITY DEFINER 및 트랜잭션 내 권한 설정](https://www.postgresql.org/docs/current/sql-createfunction.html), [Supabase DB 함수 권한](https://supabase.com/docs/guides/database/functions).
